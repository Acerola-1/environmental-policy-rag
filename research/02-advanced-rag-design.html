01 / 网上进阶 RAG 简历怎样体现深度

检索到的有效表达通常不是把解析、向量库、重排各写一条，而是解释失败场景、方案选择、个人动作和验证结果。本次核对到一份个人自述简历、一份教学案例及一个招聘机构的官方岗位页面；未获得两份可独立核验的真人履历，不将范文指标当作市场实绩。

来源与身份值得借鉴的具体写法不能照搬什么
个人网站自述简历交代异步入库、ES 候选检索与候选内向量精排，并说明使用摘要向量来处理长段落语义稀释。其日活、好评率没有附可独立复核的监控或实验记录。仅借鉴“问题→取舍”的表达，不复制数字。
代码随想录：简历教学按检索链路、数据质量、性能等维度组织，强调“做了什么改动→拿到什么结果”。示例中的 P99、召回率提升属于教学数字，未给出完整测试条件，不能当作应达到的门槛。
深圳大数据研究院：官方招聘要求图谱 RAG、增量更新、版本管理、扩展与性能优化，说明进阶要求包含持续运行和数据治理，而不仅是问答链路。该岗位的规模与架构要求不能直接套成三年经验候选人的成果。此处用于校准能力方向。

对上一版的修正：MinerU、分块、混合检索、RRF、rerank、父文档召回应合成一条“业务规模与检索底座”，其余篇幅留给真实解决过的工程问题。尚未完成的优化先作为独立设计与实战任务，不能为凑足五条而编造成果。

02 / 推荐架构：三类检索通道，加一条完整性通道

1. 文档与版本底座原始文件、解析结果、块顺序、来源和生效范围
2. 查询任务判定普通问答 / 枚举清单；抽取地区、时间、文件范围
3. 分路处理多路检索，或按文件范围逐章读取与抽取
4. 证据核对与输出条目合并、原文引用、覆盖状态与未完成项

普通问答：找到最相关的证据

词法／稀疏检索 ＋ 稠密向量检索 ＋ 图实体／关系检索 → 原文块 ID 归一 → 融合去重 → rerank → 按预算组织上下文 → 回答。

适用于概念解释、具体问题、跨文件关联。可采用 Top K / Top N，但要通过评测选择参数。

枚举任务：遍历声明范围内的材料

确定政策文件与有效版本 → 读取所有相关正文、表格和附录 → 分章抽取候选条目 → 保留适用条件后去重 → 引用校验与覆盖检查 → 结构化清单。

不能只把 Top K 调大；也不能因 rerank 分数低就静默丢弃尚未检查的章节。

职责优先选型必要边界
原件与解析产物已有文件存储；小样本可用本地目录，后续可接 MinIO 等对象存储保留原始文件及资源包。对象存储只负责保存，不自动提供检索或完整性。
文档目录、版本与顺序块PostgreSQL；个人小实验可先用 SQLite这是普通关系查询，避免为取全文再引入专门“大模型框架”。
语义／稀疏索引优先复用现有检索服务；Qdrant 是可选实现当前生产向量库与版本尚未核验。本报告不假定已经部署 Qdrant。
词法检索复用现有稀疏通道；确有需要时再加 OpenSearch BM25BM25 是相关性排序，不是“精确全量查找”；中文分词、文号规范化须验证。不必为简历堆一套新集群。
图关联发现LightRAG 的 local/global/hybrid 路径，接入其来源块结果图结果先映射回原文块。不将未验证的实体合并描述当作法律条款证据。
分章抽取与任务状态Python + LangGraph；结构化结果可用 Pydantic 校验Send 可表达动态分支；并发上限、外部限额、重试和幂等另行设计，不能认为框架自动解决。

技术依据：Qdrant 支持预取与融合查询；OpenSearch 默认关键词评分采用 BM25；LangGraph 支持 Send 与状态 reducer。以上是可用机制，不是已完成的集成。见 [4]、[7]、[8]。

03 / “精确检索”和“全文召回”到底怎么实现

精确检索有两层含义：按文号、文件 ID、版本、地区、日期做确定性过滤；随后读取这些文件的全部内容。它并不意味着能用 SQL 完全理解“治霾措施”的语义，主题判断与条目抽取仍需要规则和模型，并且可能出错。

先建立能找回原文的数据关系

下面是建议的应用数据模型，不是声称你们现有数据库已经有这些字段，也不是 MinerU 原生字段列表：

表／记录建议字段用途
documentsdoc_id、标题、文号、发文机构、行政区代码、原始链接标识一份逻辑文件；别用文件名充当唯一身份。
document_versionsversion_id、doc_id、content_hash、发布日期、生效／废止时间、替代版本、解析状态、索引状态区分修订、同名文件和有效性。未知生效／废止时间保留未知，不自动推断。
document_blocksblock_id、version_id、block_order、parent_id、块类型、页码、text、table_html、原文定位保存全文的有序组成部分；可读取父章节，也可读取整个版本。
index_mappingblock_id ↔ 向量 point_id ↔ 图来源 chunk_id；索引批次让不同通道返回同一种证据标识，便于融合、引用和失效清理。
extraction_runs任务 ID、查询范围、版本清单、已处理块、失败块、条目与引用、模型／提示词版本区分“已经检查没有条目”和“尚未处理”，支持恢复和审计。

路径 A：直接按版本读取关系库中的全文块

-- 建议数据模型的示意查询；不是在现有数据库执行的迁移或 SQL。
SELECT block_id, block_order, page_no, block_type, text, table_html
FROM document_blocks
WHERE version_id = :version_id
ORDER BY block_order;

读取的是该版本的全部已保存块，不经过相似度排序。大文件可以用 block_order 做顺序游标分批读取，再依次抽取；“取得全文”不等于一次把全文塞给模型。

路径 B：如果切片已经完整保存在 Qdrant

可用 Scroll 加 payload 条件读取某一文件版本的所有点。它不需要查询向量。示例字段是建议的应用字段：[5][6]

POST /collections/{collection_name}/points/scroll
{
  "filter": {
    "must": [
      {"key": "doc_id", "match": {"value": "示例文件ID"}},
      {"key": "version_id", "match": {"value": "示例版本ID"}}
    ]
  },
  "limit": 256,
  "with_payload": true,
  "with_vector": false
}

继续用响应中的 next_page_offset 作为下一页的 offset，直到为空；默认按 point ID 返回，取齐后仍需按应用保存的 block_order 排序。此处 256 只是示例批大小，不是性能结果。doc_id 是 payload 字段，不能误用 has_id 把它当向量点 ID。使用 order_by 时分页方式不同，不能照搬默认 offset 循环。

如果信息已经丢失，不能只改检索代码

只要保存了所有块、文件归属与顺序，就有机会从现有存储重建全文；若只保留了部分片段，或表格／附件根本没入库，需要从原始文件重新解析。缺失原件时必须记录缺口，不能声称可恢复完整内容。

MinerU 的当前官方文档已展示 4.0 统一模型：有序页面、语义块及页面定位，并区分 MiddleJson、Structured Content 和资源包；旧部署可能仍是其他协议。应保留现有版本实际产物，写适配层转为上述统一块模型，不要求先升级。独立 JSON 也不必然携带所有图片资源。[3]

04 / 完整性流程：先看全，再列全，最后证明覆盖范围

以“某年平顶山市有哪些治霾措施和标准”为例，以下是建议的新流程，不是当前项目已经实现的功能：

  1. 澄清任务范围。区分“当年发布”与“当年仍有效”；区分本市发布的文件与适用于本市的省级／国家文件。措施、排放限值、考核标准分别组织。缺少这些条件时先澄清，不能静默猜测。
  2. 得到文件清单与版本快照。按文档目录过滤，并把版本 ID 固定到本次任务。完整性通道不能只靠向量 Top K 选文件；若语料目录本身不完整，只能声明“在本次已收录文件范围内”。图谱和引用关系可提示范围外遗漏，不能自动证明目录已经穷尽。
  3. 读取正文、表格和附录。按顺序分页取回所有块。表格保留表头、单位和脚注，跨页表格需要关联检查；无法解析的页面或附件进入失败清单。
  4. 逐章节抽取候选条目。用 LangGraph Send 分派章节任务，返回结构化条目：类型、原文、适用条件、数值与单位、版本 ID、块 ID、页码。优先利用编号项、列表和表格行作为候选边界，但仍检查没有编号的普通段落。
  5. 带证据汇总，不让模型任意压缩。程序合并完全重复项，对语义近似项谨慎判重；不同适用对象、时效或阈值的标准不能合并。最终清单优先由校验后的条目集合渲染，模型负责解释而不是重新决定保留哪些项。
  6. 执行覆盖门禁。检查声明范围内每份文件、每个块是否处理完成；校验引用片段确实存在于对应版本。引用存在只能证明出处存在，不能单独证明结论正确或没有漏项。抽取遗漏仍需人工金标评测。
  7. 按实际完成程度回答。返回条目及出处、已处理文档范围、未解析／未完成项。超时后应标记“部分完成”，支持继续任务或分批展示，而不是把前几个结果当完整答案。
能保证与不能保证：程序可以校验声明范围内的文档／块是否遍历完成，但“遍历完成”不等于“语义抽取零遗漏”。更不能证明语料库包含现实中的全部政策。产品承诺应限定范围，业务效果用条目级测试验证。

文档级检索并不是新的概念：LlamaIndex 的 Document Summary Index 会取回选中文档的所有节点。但其文件选择仍可能基于摘要判断；拿到选中文档全文，不等于选中了所有应纳入的文件。无需为了这一机制迁移现有 LangGraph 技术栈。[9]

05 / 图谱如何加入，而不是再堆一个框架名

建议的分工：词法路补文号和明确术语；向量路补同义表达；图关系路补实体关联和跨文档线索。三个通道都返回可排序的 block_id 列表，再在应用层融合、去重、精排。

  1. 沿用现有业务检索索引。若已能拿到独立的稀疏／稠密结果，统一各路输出为 {block_id, rank, route, version_id}；不要直接比较 BM25、余弦和关系权重的原始分数。
  2. 图路可选择 LightRAG hybrid（local＋global），将实体／关系命中的来源 chunk 映射到 block_id。若外层已有向量路，不应无解释地再把 mix 的向量路重复加权。
  3. 应用层按路内排名做 RRF 或加权 RRF，并保留路由来源；融合的是同粒度原文证据，而不是把实体名称和文本块混在一起。LightRAG 自身的 hybrid/mix 合并机制不等于 RRF，不能把外层算法写成库原生能力。
  4. 融合前后检查版本和权限等允许范围；本次只设计版本与文档范围。最终模型输入使用有效原文，不直接把图中可能混合了新旧版本的实体描述当作政策事实。
  5. 对普通问答统一精排并控制上下文；对枚举任务，图谱只作发现与补充通道，不作为阻止逐章读取的前置筛选器。

图谱会增加构建成本，还可能出现漏抽关系、同名实体误合并与过时描述。需要通过消融回答：“它找回了哪些原来漏掉的条目，代价是多少？”若结果没有增益，不应为了简历强留图路。[10]

06 / 增量更新的价值在版本一致性，不只在少算一点向量

政策资料需要区分新文件、同文修订、废止与删除。内容哈希可以检测字节变化，但不能判断法律上的替代或生效关系，这些元数据需可靠来源或人工确认。

登记变更逻辑文档 ID、内容哈希、解析管线版本；幂等任务键
构建新版本解析、块索引、向量及图谱更新；保留旧版本
校验并发布块数与来源映射检查；成功后切换可查询版本
失效与回归清理旧索引、处理共享图元素、记录失败和重试
  • 失败可恢复。关系库记录任务状态与 outbox 事件；消费者根据幂等键重试，避免同一文件反复入库。不要把“有消息队列”当成恰好一次处理的证明。
  • 跨索引不是天然事务。向量库、关系库和图存储不共享一个数据库事务。建议先构建后发布版本清单，查询时验证证据的有效版本；清理任务可重试，失败版本不能悄悄进入结果。
  • 图的共享实体不能随文档全删。LightRAG 已有来源关联及文档删除后的受影响图元素重建机制；需要结合具体版本的 API 验证。更新文档可能需要“旧版本贡献失效＋新版本入库”，不能只追加新文本。
  • 版本过滤需要自己实现。不能假设 LightRAG 原生提供完整的政策时效隔离。初版可把图作为候选发现层、最终按版本核对原文；若要求图描述本身强隔离，还需验证分区／workspace 或独立索引策略。
  • 回归测试覆盖四种变更。新增、修订、废止、删除；检查新版本可见性、旧条款残留、同名实体污染与共享来源保留。更新耗时和恢复结果均由日志测量。

07 / 该写什么数据，以及怎么测出来

不要用一个“准确率”包办所有质量。完整性问题最关键的是条目召回率和全项覆盖率，并同时看错误条目和时效误配。下列全部是待测指标，没有任何已经取得的数值。

指标口径必须记录的条件
条目召回率正确找出的应答条目 ÷ 金标应答条目；候选、最终上下文和答案阶段分别统计问题范围、文件版本、标注规则、遗漏属于哪个阶段
答案条目精确率正确条目 ÷ 输出条目；拆分过期、范围外、无依据的错误不能靠多输出无关条目换取召回率
全项覆盖题率全部应答条目均覆盖的问题占比；无答案题单独评估同时报告是否有多余错误项；无答案题不能靠空答案抬高覆盖率
引用正确性与时效性引用能否定位且支持结论；错误版本、失效条款占比页码、块定位、原文核对及人工抽查
查询性能与成本排队、检索、首个输出和完整结果分别测 p50/p95/p99；记录 token 与费用机器、语料、模型、候选量、上下文长度、缓存、成功／失败口径
容量与更新在途请求、成功吞吐、错误／超时率；入库更新时间、失效残留和恢复记录普通问答与长枚举任务分开压测，明确是否包含外部模型请求

建议的最小对照实验

沿用前一份报告的试验规模建议：先选约 60 份公开政策、30 个问题，开发集与封存测试集分开；这只是验证流程的起点，不足以代表全行业效果。包含跨章节、多版本、表格附录、无答案和简单概念问题，人工核对金标。

组别方案回答的问题
A现有混合检索＋RRF＋rerank＋父章节召回真实基线是什么？
BA＋图关联检索单独加图能补多少遗漏，花多少成本？
CA＋限定范围的逐章抽取通道完整性路径的独立贡献是什么？
DC＋图谱发现与补充线索已有完整性通道后，图是否仍有额外价值？

普通问答的多路比较应固定解析结果、模型、上下文预算及缓存条件。枚举任务本来可能读取更多内容，不能假装成本相同：同时报告预算受控比较与实际完整流程成本。不要只挑成功案例，也不要将新分块、新模型和图谱的收益混在一起。

并发能力可以建设，但要单独验证

为长任务增加任务队列、受限 worker、模型调用信号量、超时／重试和取消机制；LangGraph checkpoint 用于状态恢复，不能代替全局任务准入和 API 配额治理。用 Locust 或等价工具逐级加压，记录实际模型限额与错误率。可以先重放固定响应测应用开销，但该结果不能称为包含真实模型调用的端到端吞吐。

活跃会话数、正在处理的 HTTP 请求数、同时发出的模型调用数与成功 QPS 是不同指标。“并发支持 150＋”“准确率 95%”等数字不能从框架特性或其他人的简历推算。后续真实测试得到什么，就报告什么。

08 / 实施顺序与简历重构

阶段最小交付物通过标准
一：先把原文取齐公开样本、统一块模型、按版本读取接口、失败块清单、初始金标与基线能找回已保存的所有正文／表格／附件块；来源可定位；不能解析的内容被显式标记
