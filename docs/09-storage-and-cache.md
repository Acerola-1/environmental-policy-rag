# PostgreSQL、Qdrant 与缓存：避免重复检索，但不复用错误答案

更新：2026-09-22。这里是目标设计，尚未部署或测出命中率/性能结果。用户已明确希望采用 PostgreSQL + Qdrant；本文件补充 Redis 缓存层及其验证条件。

## 1. 三类存储的分工

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| PostgreSQL（PG） | 文档/版本/原文块、范围元数据、来源映射、索引发布快照、任务状态与更新事件 | 不把向量点作为原文唯一副本；不依靠缓存决定法律有效性 |
| Qdrant | 原文块的稠密/稀疏向量索引、payload过滤、检索候选；可选独立语义缓存索引 | 不天然实现所有缓存过期、版本发布或业务权限机制 |
| Redis | 精确答案、检索结果、embedding结果等短期可重建缓存；可选跨进程请求合并协调 | 不作为权威原文库，不用TTL替代政策版本和授权判断 |
| LightRAG的图存储 | 实体、关系与来源块关联 | 图描述不取代原文，具体后端随固定版本验证；不强行另加未经验证的数据库 |

SQLite仅保留为无服务原型或测试替代；最终目标栈明确为PG+Qdrant，缓存使用Redis。这里没有安装数据库或改动本机运行服务。

## 2. 什么东西值得缓存

### 2.1 精确答案缓存：优先实现

同一规范化问题，在会话、查询范围、知识快照、模型/Prompt等条件一致时，返回此前完整且可引用的答案。命中可跳过query embedding、检索、重排和生成，但仍要确认请求范围与当前快照。

只缓存完整、可复用的结果。partial/error、范围未澄清、无法解析的附件、未授权资料、实时工具结果默认不缓存。无答案结果首版不缓存，避免知识更新后继续返回“没有”。

### 2.2 检索结果缓存

缓存候选block ID、版本及必要排序信息；命中后从权威原文读取/核对，可重新生成回答。它节省检索与重排，不一定节省生成。检索缓存和答案缓存的命中率必须分开。

### 2.3 embedding与文档处理缓存

query embedding由规范化文本、embedding模型版本和维度决定；文档解析/分块由原文件哈希、解析版本及配置决定。入库重复与提问重复是两个问题，不能算成同一种问答缓存收益。

### 2.4 语义答案缓存：后置、保守、先影子测试

对普通概念问答，在硬范围相同的候选中查相似问题。相似只表示候选，不证明答案可替换；数字、否定、主体、时间和条件仍可能不同。

政策枚举、标准阈值、跨版本比较首版关闭语义答案复用，可使用严格的精确缓存。不能拿“2024年样例市甲有哪些措施”的答案去回答2025年或样例市乙。

供应商的prompt缓存是另一层：复用模型输入前缀的计算，通常仍会执行模型生成；不能把其节省比例当作我们的RAG请求免调用比例。

## 3. 缓存键不能只有query hash

建议构造规范化JSON后哈希；以下是应用字段设计，不是已存在的API：

```text
namespace / dataset_kind / user_scope / authorization_epoch
canonical_query / query_mode / conversation_digest
region / time_semantics / resolved_as_of / document_scope
knowledge_snapshot_id / retrieval_config_version
embedding_model_version / reranker_version
answer_model_version / prompt_version / output_schema_version
```

- 个人公开验证阶段可使用固定的 `user_scope=local-public`，不声称已实现生产RBAC；多用户时必须接入实际授权范围和权限变更版本。
- “今年”“最新”等相对表达先解析为具体时点，并进入key。无法确认范围时不缓存。
- 规范化仅做安全的空白、编码等处理；不能删除日期、单位、否定词或条件来提高命中率。
- 对依赖会话的问题，带会话摘要版本或完整上下文digest；不能把“那它呢”当作独立相同问题。
- 调整top-k、融合权重或索引快照后应进入不同的缓存命名空间，避免缓存掩盖新方案效果。

## 4. 一次请求的目标流程

```text
明确任务与访问范围
  -> 从PG读取/固定已发布知识快照
  -> 精确答案key查Redis
       命中且完整/未过期/快照适用 -> 返回答案+来源
       未命中 -> 对允许的普通问答做可选语义候选查找
                   通过范围与复用核验 -> 返回
                   未通过 -> 查检索/embedding缓存
                               -> 必要时执行实际检索、精排和生成
                               -> 仅将符合缓存策略的完整结果写入
```

缓存坏了不是数据没了。Redis不可用时应按既定负载策略回退源链路或明确拒绝，不能返回未知版本的旧值。

## 5. 如何利用Qdrant做语义缓存，而不再添一套向量栈

若阶段二需要语义缓存，可把历史问题向量放在独立的 `semantic_cache` collection，payload保存cache key、知识快照、范围、模型版本和绝对过期时间。答案与引用保存在Redis；查询先做硬元数据过滤，再做相似度候选检索。

这是一种建议组合，不是Qdrant开箱即用的缓存管理功能：

1. 向量命中后仍查Redis；Redis已过期或缺失就按miss处理。
2. 应用明确检查 `expires_at`，并清理残留向量点；不能假设设置payload时间就会自动删除。
3. 模型向量版本和维度变化时使用新索引，不复用不兼容的向量。
4. 语义查找通常仍需要问题embedding；不能声称每次命中完全没有模型/embedding费用。
5. 如以后选RedisVL的向量语义缓存，则重新比较运维成本，不同时维护两套等价缓存向量索引。

RedisVL官方资料提供阈值、TTL和过滤机制，但它的cosine distance阈值与其他服务的similarity score含义可能相反，不能照搬一个0.8或0.2当质量保证。

## 6. 失效与并发击穿

### 版本失效优先，TTL兜底

PG是已发布快照的权威来源。新版本构建并校验成功后切换快照，后续请求使用新key；旧key即使尚未删除也不可被新快照命中。随后异步清理旧值与图来源。

若为了速度在Redis镜像快照指针，必须验证发布一致性，不能把异步失效通知当强一致。权限变化同理，需更改实际授权版本；TTL不能防止TTL窗口内的越权。

知识版本、生效时间、模型/Prompt与检索配置变化都可能使答案失效。自动滑动TTL可能让热点旧答案长期存活，因此设计独立的绝对最大年龄；当前不预设具体TTL，先看业务时效需求。

### 同key请求合并

同一缓存key同时miss时，合并为一次填充任务，其余等待或安全回退。单进程可用任务表/锁；跨进程需要带唯一所有者、过期和安全释放的协调机制。锁失效不能让晚到的旧任务覆盖新快照。

请求合并、缓存命中、模型并发上限是不同指标。不能用“Redis很快”推导出系统能支持多少并发。

## 7. 必须补的测试

| 场景 | 预期 |
|---|---|
| 问题、范围、快照、会话完全相同 | 精确缓存命中；源检索/重排/生成调用计数为0 |
| 相同文本但地区、年份、用户范围不同 | 不跨范围复用 |
| 同query但知识快照、Prompt或模型变化 | 不命中旧版本 |
| 最新/今年等相对日期发生变化 | 重新解析时点，旧key不复用 |
| 枚举/阈值问法只是相似 | 默认不走语义答案缓存 |
| 命中向量但Redis答案已过期 | miss并安全回源，不返回残留值 |
| partial/error/范围未澄清 | 不进入可服务答案缓存 |
| 同key并发miss | 合并填充；异常时释放/超时恢复，输出仍有明确状态 |
| 更新发生在填充期间 | 不把旧快照结果写入新快照key |
| 缓存服务不可用 | 有界回退或明确错误；不引发无限回源风暴 |

这些是待实现的测试，不属于现有48项评分器测试。

## 8. 质量和性能报告必须分组

冷缓存、完全相同请求热缓存、近义改写、范围冲突、版本更新、自然重复分布分别运行。记录精确/语义/检索/embedding各层hit与miss，语义误命中率、过期/越界复用、实际节省的源调用、查缓存开销、端到端延迟和总费用。

重放大量相同问题得到的高命中率，只说明该重放集的重复分布；不能当成真实用户命中率。缓存测试不能与检索算法冷启动消融混在一起，避免缓存直接返回旧答案掩盖新算法。
