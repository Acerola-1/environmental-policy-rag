# 架构与技术栈

## 1. 先理解两个不同的问题

普通问答寻找最相关的少量证据；枚举问答需要检查声明范围内是否还有遗漏。父章节召回解决局部上下文，不保证相关文件、章节、附件都进入结果。把 Top K 调大或换图谱不能替代完整性流程。

```text
文件 -> 原件与解析产物 -> 文档/版本/有序块 -> 检索索引
                                      |
问题 -> 范围与任务判定 -----------------+
       |                               |
       + 普通问答                       + 枚举问答
         稀疏/词法 + 向量 + 图候选         固定文件与版本范围
         映射到原文 block_id              逐章读取正文/表格/附件
         融合、去重、rerank               结构化抽取、条件保留
         预算内上下文                     合并、引用与覆盖核对
       |                               |
       +--------- 有范围与出处的回答 -----+
```

图只负责候选发现，不把实体合并描述当成政策原文。两路共享文档身份、版本、来源和评测协议。

## 2. 最小栈与后续栈

| 层 | 起步建议 | 后续选择/理由 |
|---|---|---|
| 语言 | Python 3.11+；离线工具只用标准库 | 与已有 Python Agent 经验衔接 |
| 原件 | 本地只读文件，使用分类目录 | 需要跨进程访问再接 MinIO/其他对象存储 |
| 目录与块 | PostgreSQL（目标栈已选） | 保存文档、版本、原文块和发布快照；离线JSONL无需服务，SQLite仅作标明的测试替代 |
| 解析 | 首批使用MinerU精准API取得JSON与资源包 | 优先复用固定版本LightRAG的现成转换，仅补业务映射；实际协议先核实，不自研OCR |
| 稀疏/词法 | 复用现有可复现方案或实现小样本基线 | Qdrant 稀疏通道或 OpenSearch BM25；中文分词、文号应单独测 |
| 稠密/稀疏索引 | Qdrant（目标栈已选） | 与PG原文通过block_id映射；不声称过去生产已经使用 |
| 问答与检索缓存 | Redis | 精确复用优先，按范围和快照隔离；语义缓存后置验证，见缓存专题 |
| 重排 | 根据真实服务接口写适配器 | 不是所有供应商都支持同样的 rerank endpoint |
| 图候选 | 采用固定版本LightRAG；可提前引入，图检索效果验证后置 | 先用 hybrid 图路，与外部向量路避免重复加权；引入转换依赖不自动触发构图 |
| 编排 | Python 函数开始；复杂分支再接 LangGraph | Send 做按章节分发，reducer 聚合；全局限额由应用控制 |
| 接口 | 数据与算法可独立测试后再加 FastAPI | 不先花时间做 UI、登录、后台管理 |
| 异步任务 | 首轮有界本地 worker | 需要跨进程恢复再选任务队列；沿用熟悉技术优先 |
| 测试 | unittest、固定输入、独立裁决 | 负载阶段可用 Locust，前提是 API、成本和环境已确认 |

不要求一次安装表中所有服务；此表不是依赖锁文件。

## 3. 数据模型

先实现 `documents`、`document_versions`、`document_blocks`；样例 JSONL 的字段见 [数据契约](05-data-contracts.md)。运行型数据库可在其基础上补充内容哈希、原件路径和管线版本。

- `doc_id`：逻辑文件，修订前后不应因文件名变化而丢失身份。
- `version_id`：不可变内容版本。当前小样例要求在数据集中唯一；生产可以命名为 `doc_id:content_hash`。
- `block_id`：对应版本内的可定位原文块，不直接用向量点 ID 冒充。
- `block_order`：同一版本内稳定的阅读顺序；父块引用用于章节扩展。
- 历史有效时间与索引发布状态分开：政策已经废止，不代表历史查询不能读取它。
- 另建 `index_mapping` 关联向量 point ID、图来源 chunk ID 和 block ID。

按全文读取的示意 SQL：

```sql
SELECT block_id, block_order, page_no, block_type, text, table_html
FROM document_blocks
WHERE version_id = :version_id
ORDER BY block_order;
```

它取得的是保存过的全部块，并不能恢复未解析/未保存的内容。大文件按顺序分页，不必一次进入模型上下文。

## 4. 多路融合的接口

建议每个候选统一成：

```json
{"block_id":"示意ID","version_id":"示意版本","route":"dense","rank":1}
```

词法、向量、图各自在路内排序；应用层用排名融合，避免直接比较不同含义的分数。图实体/关系必须先映射到来源块。相同 block 合并时保留来源通道，方便解释“哪一路补回了它”。

LightRAG 的 hybrid/mix 原生合并不是 RRF。若自己的应用采用 RRF，应将其标为外层实现，而不是写成上游库功能。

## 5. 枚举路径的状态

建议状态包含 `run_id/query/scope/version_snapshot/pending_blocks/processed_blocks/failed_blocks/items/evidence/warnings`。

- 范围判定后固定版本快照，避免一次查询中混入更新后的另一版本。
- 逐块返回“已处理但无相关项”或“处理失败”，不要用空列表同时表示两者。
- 返回条目保留适用对象、条件、时间、阈值与单位。
- 引用原文存在只是必要条件，不是语义正确或零遗漏的证明。
- 未处理完、解析失败或范围不确定，应显示部分完成状态，不输出无条件的“全部”。

## 6. 版本化增量更新

内容哈希检测变化；法定替代、生效、废止关系需要来源或人工确认。建议：登记变更 -> 幂等任务 -> 构建新版本各索引 -> 验证映射 -> 发布版本 -> 失效清理与回归。

关系库、向量库和图没有天然统一事务。先构建后发布；查询按有效版本检查证据；清理可重试；图中共享实体按剩余来源处理，不得随一份文件简单全删。新增、修订、废止和删除应有各自测试。
