# 质量评测、消融与负载验证

## 1. 三类验证不要混在一起

- 单元/冒烟测试：检查程序逻辑，使用手工可控样例；不代表模型质量。
- 质量评测：真实模型输出 + 固定题集 + 独立金标与裁决；公开与合成分别统计。
- 性能测试：固定环境下的请求、成功吞吐、延迟、错误与费用；不能用活跃会话数替代处理容量。

目前只有第一类的离线启动工具，不存在已测准确率或并发成绩。

## 2. 质量指标

设每题金标集合为 G，预测条目列表为 P；经过人工裁决的唯一正确金标命中为 H。

| 指标 | 定义 | 特别注意 |
|---|---|---|
| micro 条目召回 | 全部题的 H 总数 / G 总数 | 失败题仍在分母；不能只统计成功样本 |
| macro 条目召回 | 对可回答题逐题 H/G 后平均 | 无答案题分开，不人为设为100% |
| 条目精确率 | 唯一正确命中总数 / 所有输出条目数 | 重复答案不增加分子，无答案题误答进入分母 |
| 全项覆盖题率 | 状态 complete 且覆盖全部金标的可回答题占比 | partial 即使偶然覆盖金标也不宣称完整执行 |
| 完全正确题率 | complete、金标齐全、无错项/重复、引用均支持且无错误版本的题数 / 全部题数 | 无答案题需 complete 且无输出；与“覆盖了但夹杂错误”区分 |
| 无答案题正确率 | 无答案题中 complete 且输出为空的比例 | error/timeout 的空输出不能算答对 |
| 引用支持率 | 人工判定引用支持结论的输出条目数 / 输出条目总数 | 引用文本存在不等于支持结论 |
| 错误版本率 | 使用不适用版本的输出条目数 / 输出条目总数 | 历史问题使用旧版本可能是正确答案 |

分母为0应显示 null/不适用，不显示100%。保留每题结果，便于发现大题主导 micro 分数等情况。

当前评分器依据人工 judgments 计算；不自行完成语义判定。相同金标多次输出最多计一次命中。partial/error 的真实正确项可以计入局部召回，但不能计为完整覆盖。

## 3. 分阶段定位漏项

建议后续保存这些阶段的证据块清单：解析输出、每路候选、融合后、重排后、最终上下文、答案条目。

对每个漏掉的 gold item 问：原件是否有？解析是否保留？其证据是否进入候选？是否被重排或预算截掉？进入上下文后是否被模型漏写？归因不能仅凭最终答案猜测。

## 4. 四组对照

| 组别 | 方案 | 用途 |
|---|---|---|
| A | 现有混合检索、RRF、rerank、父章节召回 | 实际基线 |
| B | A + 图关联候选 | 图的独立贡献 |
| C | A + 范围内逐章读取/抽取 | 完整性路径的独立贡献 |
| D | C + 图发现与补充线索 | 完整性路径已有后，图是否还有增益 |

A/B 比较应固定语料、分块、模型、重排、缓存和上下文预算；不要同时升级所有组件。C/D 可能扫描更多内容，必须同时报告总 token、时间和费用；不能假装多读全文没有成本。

分块策略、图路 local/global/hybrid、RRF 权重等一次只改变可解释的因素。用开发集选参数，封存测试集不反复调参。样本过少时给出逐题结果和限制，不只给一个漂亮百分比。

## 5. 运行证据目录

建议每次授权实验写到独立路径：

```text
runs/<dataset-kind>/<run-id>/
  run-manifest.json        # 数据、代码、模型、配置、时间、预算
  predictions.jsonl       # 每道题都有记录，失败不丢弃
  retrieval-traces.jsonl   # 各阶段证据与删除原因
  judgments.jsonl         # 裁决与复核记录
  metrics.json
  errors.jsonl
  case-review.md          # 成功、失败与原因分析
```

这是未来运行目录约定。当前 demo 仅输出指定的评分 JSON，不会假造这套完整溯源材料。

run-manifest 至少记录 dataset_kind、split、样本哈希/版本、代码提交、解析版本、模型/接口、embedding维度、候选数、token预算、缓存、是否实际调用模型、裁决方法及执行者。原始秘密与受限文本不写日志。

## 6. 性能测试前先定义对象

分别测试普通问答和枚举任务。至少区分：

- 请求队列中的等待数量；
- 正在服务端处理的请求/任务；
- 实际同时进行的模型调用；
- 每秒成功完成的请求数；
- 活跃用户/会话数量。

上述量不等价。LangGraph 多分支也不自动等于服务能承载高并发。

## 7. 建立可测的服务边界

先实现：任务准入、受限队列、模型调用并发上限、超时、重试上限与退避、取消、partial/error状态。根据供应商 RPM/TPM 设置限制，防止429后立即重试造成风暴。

每个请求记录到达、开始处理、检索结束、首个输出、整体结束、最终状态。仅有HTTP200不够，枚举尚未完成不能被统计为成功完成。

## 8. 两层负载实验

### 层 A：应用自身开销

可用固定回放响应隔离数据库、调度、序列化等开销。明确报告“未包含真实外部模型调用”。这不能成为端到端吞吐证据。

### 层 B：真实模型端到端

使用已核验API和允许外发的数据，事先确认最大请求数、测试时间和费用。按递增并发逐级测试，遇到预设错误率、延迟或费用阈值即停止。工具可选 Locust，但本目录尚未提供负载脚本。

记录硬件、进程/worker、语料、索引、模型、输入/输出长度、缓存、候选数、网络及供应商限额。记录请求分布与超时；不要只记录成功请求的好看P95而丢掉超时。

## 9. 必报结果

成功吞吐、失败/超时/限额率；排队、检索、首个输出、完整结果各自的p50/p95/p99；总token/费用和单次成本。样本不足时说明分位数不稳定。

更新侧另测：新增、修订、删除完成耗时、旧内容残留、重试次数和恢复结果。把索引构建成本与查询成本分开。

## 9.1 缓存必须单独分组

冷缓存、精确重复热缓存、语义近似、范围冲突、知识更新及自然请求分布分别测。统计各层命中、错误复用、实际跳过的源调用、缓存开销、端到端时延及费用；不要用Redis读取时间当作整个RAG响应时间。

[缓存实现与边界](09-storage-and-cache.md) 给出需补的测试；[行业数字与研发门槛](10-industry-metrics-and-targets.md) 分开记录外部参考、人为验收目标和个人实测。目标稿不得采用外部数字或50%的开发目标冒充成绩。

## 10. 哪些数据才能进入简历

同时有数据范围、配置、时间、原始结果、贡献边界和可复查代码；并说明这是个人本地验证还是生产观测。百分比与百分点不混用。未测写“待测”，目标写“目标”，不得从demo、官方论文或别人简历推算自己的成果。
