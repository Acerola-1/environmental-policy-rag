## Context

本阶段把 stage-02 的不可变原文和 stage-04/stage-06 的检索索引接入可恢复生命周期。内容存储、基线和图检索都必须先有实际验收证据，不能根据框架宣传推断增量一致性。当前只有离线工具及 8 份、139 页 PDF，3 份、28 页未解析；全部上述业务功能均未实现。

参考：[路线](../../../docs/04-step-by-step.md)、[架构](../../../docs/01-architecture-and-stack.md)、[数据契约](../../../docs/05-data-contracts.md)、[更新与成本评测](../../../docs/06-evaluation-and-load-test.md)、[验收](../../../docs/07-acceptance-and-evidence.md)。以下身份、状态、接口和证据位置均为计划，具体契约需实施前与上游对齐。本轮保留原 docs，不修改代码/配置或 `.openspec.yaml`。

## Goals / Non-Goals

### Goals

- 分离物理内容、法律效力、解析变化及索引可见性，能够复现历史查询。
- 实现幂等构建、校验与 PG 原子发布，失败时旧 snapshot 仍能读取同一批原文、向量及图资源。
- 让逻辑快照有可验证的物理资源支撑，正确处理读者引用、并发写者与清理重试。
- 向后续缓存阶段交付稳定的发布版本契约，不反向依赖缓存实现。

### Non-Goals

- 不实现跨 PG/Qdrant/LightRAG 的分布式原子事务，不宣称恰好一次外部写入或计费。
- 不把哈希当法律效力裁决，不自动替用户做不可逆删除，不承诺无限历史保留。
- 不实现 stage-08 缓存或 stage-09 服务/负载治理；容量测试不属于本阶段功能竞态测试。
- 本轮仅规划，不实现、安装、联网、读密钥、启动服务或调用模型，不运行项目测试。

## Decisions

### 1. 身份与时间分层，法律元数据进入快照

计划沿用稳定 doc_id；内容 version_id 标识不可变政策文本，内容哈希用于发现字节/内容差异但不证明修订、废止或替代。同一内容可能更正法律日期而不变哈希，不同哈希也可能仅是扫描/封装差异，需保留来源与人工核实结果。

解析版本标识解析器/配置及输出块集合，同内容重新解析产生新解析身份，不覆盖旧 block_id 的文本。每种索引的 generation 标识不可变构建结果及模型/索引配置；同一内容/解析也可因 embedding 或图配置变化而重建。snapshot 是不可变清单，精确列出内容/解析身份、法律元数据修订标识、PG 块集合及词法/向量/图 generation 和映射。publication_revision 是 PG 发布序号，不等同于上述任一版本。

当前有效查询按已核实法律有效区间选内容版本，发布日期筛选另有语义；未知效力待核实，不编日期。历史法律时点与“当时发布的索引视图”是两个维度，应分别指定 as_of 和可选 snapshot，不能相互替代。

原因：一个 version 字段无法表达独立演进。替代方案是文件名/哈希同时承担政策版本和索引状态，会让重解析改写历史、法律更正不失效，故不用。

### 2. 幂等任务账本与隔离构建

计划 PG 账本记录任务 ID、逻辑操作、目标内容/解析/索引配置、幂等键、期望父 publication_revision、构建标识、各阶段状态、错误及尝试次数。幂等键按操作语义和目标身份定义，不能只用内容哈希而漏掉同内容法律元数据更新。重复提交返回已有任务/结果；失败重试复用同一逻辑目标和稳定外部标识。任务阶段区分 registered、building、validated、published 与 failed/retryable、cleanup_pending，发布成功和清理完成分别显示。

PG 块/映射、Qdrant 点及 LightRAG 来源贡献先写入未发布 generation。每个副作用均以稳定身份可重放，成功状态应能核对远端结果；仅“PG 已记录”不代表外部写成功。限制重试次数，超限明确停止；并发恢复需要带尝试代次/占有权校验，过期 worker 不得覆盖新任务状态或标记可发布。

原因：进程会在外部成功、账本未提交时崩溃。替代方案是失败从零无条件重建或认为本地检查点提供恰好一次，会重复计费和写脏状态，故不用。

### 3. 隔离资源可读，才能原子发布指针

先 build，再核验预期/实际块与来源映射、scope/版本、模型/维度配置、向量/图可读性及原文引用；缺失、残留或混版均阻止 validated。发布的必要资源应已持久可读，并在生命周期内不可变。可按实际后端选择独立 collection/namespace、隔离数据库空间或可证明不可变的 generation 分区；仅在共享可变索引上贴 snapshot_id 不构成隔离。共享实体 summary 若原地更新会改变旧图视图，必须版本化来源/派生内容或采用隔离重建。

PG 事务只处理自身的 snapshot 清单、发布记录及当前指针，用期望父 revision 的比较并交换或等价锁定保证原子切换。不先后改多个库的“当前 alias”再假称同时生效。所有路从 PG 一次固定的发布视图读取指定 generation，不独立查询各库的 latest。

若任一构建/校验失败，指针不变，旧 snapshot 仍可读；发布后发现问题可经校验重新发布旧资源的视图，但分配新的单调 publication_revision，避免回退重用旧发布标识。图后端不满足隔离能力时，优先评估获准的全量隔离重建，否则阻塞发布，不承诺另装图数据库。

原因：只有 PG 能事务性管理发布真相。替代方案是跨库两阶段提交的虚假承诺、逐库 alias 切换或先删旧再建新，会暴露部分更新，故不采用。

### 4. 读者引用与并发发布必须实际测试

计划读者在 PG 事务内读取发布指针并取得对应 snapshot 的持久引用/租约，两步与清理资格判定串行化；输出携带 snapshot_id、publication_revision，分页、枚举恢复及最终引用都沿用该视图。若用租约，约定续租、期限与失租后的终止规则；恢复不能假定旧引用仍有效，应重新申请同一快照，已清理则明确不可用，不偷偷换新。

多个快照可引用相同不可变 generation；清理必须同时检查当前发布指针、历史保留策略、所有快照资源引用和在途读者。逻辑快照清单不等于物理资源已保留。清理者在事务内标记候选为 deleting 后拒绝新引用，已有合法引用阻止删除；逐库删除后再记账。超时租约的读者必须停止读取/续页，不能继续使用已释放资源。

并发发布以同一分区/知识目录的 expected_revision 为竞争条件，只允许一项成功，失败者记录 conflict；需从新父快照重新计算合并结果并重新校验，不能重试时盲覆盖其他更新。元数据重试也受同一规则约束。拟用受控时序/故障注入测试两个发布者、查询固定视图与 GC 竞争，不做未授权负载。

原因：只有快照 ID 而无引用保护仍会读到已删资源。替代方案是依赖 TTL 猜测查询已结束，或最后写入者胜出，会丢更新/破坏旧读者，故不用。

### 5. 新增、修订、废止与删除采用不同语义

新增引入新 doc/内容及索引；修订创建新内容版本，并以经核实的效力关系控制当前查询，旧版本保留供历史查询；废止仅改变经核实的法律适用状态，不等于物理删除，必要时发布新法律元数据快照并复用不变索引资源。替代关系须有来源证据，不能从哈希推断。

删除默认是获准的目录撤回/逻辑 tombstone，阻止新当前范围继续纳入；历史是否可读取决于明确保留/授权策略，不自动等同废止。物理删除须另行授权，只有不被保留历史或在途引用占用时才进入清理；若要求立即禁止访问历史，应显式撤销访问并让旧请求失败，而不是让被删资源继续作为合法证据。输出说明历史快照不可用，不能伪装成无答案。

图清理按文档版本的来源贡献移除；仍被其他来源支持的实体/关系保留并重算必要派生内容，不能按实体名整删。新 generation 去除旧贡献但旧历史 generation 不被原地修改；若需模型重算仍经过费用授权。Qdrant 点、图贡献、PG 映射清理分步记录，可幂等重试；失败残留不能通过新 snapshot 的引用校验进入当前答案。

原因：法律失效和数据销毁不是同一操作。替代方案是一律删整文件图元素或保留所有旧内容而不筛版本，分别损害共享来源和当前适用性，故不接受。

### 6. 发布版本接口先行，缓存作为单向消费者

计划提供可由库调用的“取得已发布视图/取得指定历史视图”契约，至少返回 snapshot_id、publication_revision、内容/解析与各 generation 清单标识、法律元数据修订和就绪状态；获取过程与引用保护协作，不要求先有 HTTP 服务。每次影响回答的内容、解析、法律元数据或检索/图配置发布都必须得到新的发布序号；重复已完成任务不多发一次。

stage-08 可把 snapshot_id/publication_revision 纳入缓存 key，并另加查询、会话、授权/范围和模型配置维度；发布事件可辅助失效但不是唯一正确性来源，Redis 故障不影响本阶段发布与查询。接口验收只需固定响应和版本变化测试，不等待 stage-08 缓存实现，避免依赖环。

原因：仅 TTL 或异步通知可能漏掉更新。替代方案是本阶段直接实现缓存和失效广播，会扩大范围且产生反向依赖，故留给下游。

## Risks / Trade-offs

- 多 generation 和历史保留提高存储、构建 token 与时间成本；用可审计的保留策略和引用释放控制，不能以省空间破坏快照语义。
- LightRAG 固定版本/后端能力尚未核实，隔离重建可能成本更高；上游不提供证据则本阶段阻塞。
- 校验通过不代表服务永不故障；读取失败应显式 error/partial，不能临时混入别代索引。旧版本是否可回退必须重新固定视图。
- 独立任务重试可能重复外部模型调用，需记录费用与请求状态；PG 事务不保证跨库或计费恰好一次。
- 保留策略、租约期限、法律元数据核实和物理删除授权需实施前明确；未知部分不以默认永久保留/立即删除掩盖。

## Migration Plan

首次实施读取上游原文与 A/图配置，盘点可用资源并建立初始不可变 snapshot，先验证当前与历史查询，再开启新 generation 发布。未验证连接前不操作用户容器；不清库、不原地覆盖旧资源。升级期间保持原读取入口可用，无法证明旧资源隔离时暂停迁移。

回退通过新的 PG 发布记录指向已验证可用资源，不倒退 publication_revision；保留失败构建与清理日志供恢复。迁移、模型构建、真实服务测试需另行授权，本轮不执行。
